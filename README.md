# Ипотечный ассистент

Бэкенд ассистента ипотечного банка. Проект к воркшопам второго модуля профессии
«LLM-разработчик» на Хекслете.

Архитектура и решения: [docs/architecture.md](docs/architecture.md), [docs/adr/](docs/adr/).

## Эталон по встречам

После каждой встречи здесь появляется тег с решением домашнего задания: `workshop-1`,
`workshop-2` и так далее.

```sh
git clone https://github.com/Obolduy/mortgage-assistant.git
cd mortgage-assistant
git fetch --tags

# начать следующий шаг с эталона
git checkout -b my-work workshop-1

# сравнить свое решение с эталоном
git diff workshop-1 -- app/
```

## Что есть в тегах

`workshop-1`:

- Каркас на FastAPI: типизированные настройки, пул соединений, структурные логи.
- Postgres с pgvector и Temporal в Docker Compose.
- Миграции SQL-файлами и свой раннер.
- Проверки живости и готовности.
- Таблица кредитов с пятью тестовыми кредитами.
- Калькулятор в целых копейках: график, досрочное погашение (сократить срок или платеж), смена
  даты платежа.
- `GET /loans/{id}` и `GET /loans/{id}/schedule`.

`workshop-2-start` – код, который разбираем на второй встрече, с него начинается домашка:

- Клиент модели: повторы и таймаут живут в HTTP-клиенте, у прогона агента свой общий таймаут.
- Агент на OpenAI Agents SDK с инструментами `get_loan`, `get_schedule`,
  `simulate_early_repayment`. Номер кредита приходит из контекста клиента, модель его не выбирает.
- Контракт ответа `AssistantAnswer` и `POST /ask`.
- Бюджет ходов агента: исчерпан – вопрос уходит сотруднику.

## Запуск

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/) и Docker. Для `POST /ask` – локальная модель:
[LM Studio](https://lmstudio.ai/) с `gemma-4-e4b-it` на `http://localhost:1234`.

```sh
cp .env.example .env   # порт 5434 занят? поменяйте PG_PORT и DATABASE_URL
make install           # зависимости из uv.lock
make infra             # Postgres с pgvector и Temporal
make migrate           # повторный запуск напишет «Новых миграций нет»
make api               # http://localhost:8000/docs
```

```sh
make lint
make test   # тестам нужна поднятая база с миграциями, модель не нужна
```

## Как проверить себя

- `make test` и `make lint` зеленые.
- Повторный `make migrate` ничего не применяет.
- `GET /health/ready` отвечает 200 и версией `vector`.
- `docker compose -p mortgage-assistant stop db`: `/health/live` – 200, `/health/ready` – 503.
- Без `DATABASE_URL` приложение не стартует.
- `GET /loans/1/schedule`: первый платеж 5 505 431 копейка (55 054,31 ₽).

## Деньги

Все суммы – целые копейки, ставка – базисные пункты: 12% годовых = `1200`. Почему так –
[ADR-0001](docs/adr/0001-agent-stack.md).

## Этапы проекта

- Ветка `main` — первое ДЗ.
- Ветка `hw2` — второе ДЗ на основе учебного тега `workshop-2-start`.

## ДЗ 1: каркас и кредитный калькулятор

- Каркас приложения на FastAPI и управление зависимостями через uv.
- Postgres с pgvector и Temporal в Docker Compose.
- Пул соединений и проверки живости и готовности приложения.
- SQL-миграции и пять тестовых кредитов.
- Кредитный калькулятор: график платежей и два режима досрочного погашения.
- Денежные расчёты в целых копейках.
- Тесты калькулятора и проверок приложения.

## ДЗ 2

Реализованы разбор и исправление ответа модели, проверка денежных сумм,
порог уверенности, задачи с ключами идемпотентности и заявления
на смену даты платежа через Temporal.

Агент умеет проверять возможность смены даты и подавать заявление.
Решение по заявлению принимает сотрудник.

Для запуска нужны Postgres и Temporal: `make infra`, затем `make migrate`.
В отдельных терминалах запускаются `make worker` и `make api`.

Для тестов нужны Postgres и Temporal. Модель не требуется:
её вызовы подменяются в тестах.

Проверки: `make test` и `make lint`.

## Домашняя работа 3: документы и поиск

Ветка `hw3` продолжает работу из ДЗ 2.

### Что реализовано

- Таблицы документов и чанков, векторы размерности 768.
- Полнотекстовый индекс для русского языка и индекс кода программы.
- Загрузка PDF, DOCX и XLSX через API.
- Разбор и построение эмбеддингов в Temporal.
- Защита от повторной обработки одинакового файла по SHA-256.
- EmbeddingGemma на CPU, загрузка модели один раз на процесс.
- Пересчёт отсутствующих или устаревших векторов через `make reindex`.
- Векторный, полнотекстовый и гибридный поиск.
- Объединение результатов через RRF в SQL.
- Приоритет точного кода программы и фильтр по имени файла.

### Подготовка модели

На Hugging Face нужно принять условия доступа к модели:
https://huggingface.co/google/embeddinggemma-300m

Затем выполнить:

```bash
uv run hf auth login
```

Используется `google/embeddinggemma-300m` на CPU.
Первый запуск требует скачивания модели.

### Запуск

Установить зависимости и подготовить инфраструктуру:

```bash
make install
make infra
make migrate
```

Настроить `.env` по `.env.example`.

В отдельных терминалах запустить:

```bash
make worker
```

```bash
make api
```

Temporal UI: http://localhost:8233

### Загрузка документов

```bash
curl -i -F "file=@data/tariffs.xlsx" \
  http://127.0.0.1:8000/documents
```

Ответ — HTTP 202 с ID документа.

Проверка состояния:

```bash
curl http://127.0.0.1:8000/documents/DOCUMENT_ID
```

Статусы успешной обработки:

`uploaded → parsing → embedding → indexed`

Скан без текстового слоя и неподдерживаемый формат получают
`rejected` с причиной. Ошибка шага после исчерпания повторов
приводит к `failed`.

Повторная загрузка одинаковых байтов возвращает тот же документ
и не создаёт второй процесс.

В `data/` находятся пять поддерживаемых текстовых документов
и скан `income_statement_scan.pdf` для проверки отказа.

### Поиск

```bash
curl -G http://127.0.0.1:8000/search \
  --data-urlencode "q=ставка по IP-FAMILY-6" \
  --data-urlencode "mode=hybrid"
```

Параметры:

- `q` — поисковый запрос.
- `mode` — `hybrid`, `vector` или `fts`.
- `filename` — необязательное точное имя файла.
- `limit` — количество результатов, от 1 до 100, по умолчанию 10.

`fts` означает полнотекстовый поиск и не требует загрузки модели.

В ответе возвращаются текст чанка, файл, раздел, страница,
лист и строка таблицы, если они доступны.

`similarity` — косинусная похожесть векторного результата.
`score` — балл ранжирования RRF.

Порог применяется только к векторной ветке:
`SEARCH_SIMILARITY_THRESHOLD=0.30`.

Обоснование: [ADR-0003](docs/adr/0003-search-threshold.md).
Замеры: [отчёт](docs/evaluation/search-calibration.json).

### Пересчёт векторов

```bash
make reindex
```

Пересчитываются отсутствующие векторы и векторы другой модели.
Повторный запуск без изменений выводит `Обновлено векторов: 0`.

### Проверки

```bash
make test
make lint
```

В тестах эмбеддер подменяется, веса модели не загружаются.
Интеграционным тестам нужны работающие PostgreSQL и Temporal.

Для повторения замеров с настоящей моделью:

```bash
uv run python -m scripts.evaluate_search
```

Отчёт сохраняется в `/tmp/bank-search-calibration.json`.
